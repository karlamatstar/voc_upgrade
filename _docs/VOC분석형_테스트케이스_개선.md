# VOC 분석형 테스트 케이스 개선

## 변경 목적

기존 TC-01~TC-12의 질문 상당수가 `voc.csv`의 고객 불만 문장을 거의 그대로 사용해,
정확한 문장 매칭 여부만 확인하는 쉬운 평가가 될 수 있었다. 프로젝트의 핵심 목적인
VOC 검색·종합·요약·정책 개선 능력을 평가하도록 질문을 분석 요청형으로 개선했다.

## 코드 흐름 재분석

- `test_cases.json`은 질문과 기대 결과의 단일 원본이다.
- LLM Judge는 실행 시작 시 20개 케이스를 메모리에 읽는다.
- TC-01~TC-18은 실제 Judge 대상이다.
- TC-19~TC-20은 pytest 장애 검증 전용이다.
- pytest E2E에서 TC-01~TC-10을 반복 실행하던 코드는 앞선 작업에서 제거됐다.
- 일반 live 케이스는 Interpreter 결과와 질문 기반 보조 검색어를 함께 사용한다.
- `expect_no_data=true`인 TC-17~TC-18은 보조 검색어를 강제로 추가하지 않고 실제
  무관한 데이터에 대해 Retriever가 0건을 반환하는지 확인한다.
- Judge 프롬프트에는 질문과 함께 `expected_intent`, `expected_keywords`,
  `required_output`, `prohibited_output`이 전달된다.

## 유지한 유형과 개수

| 유형 | 개수 | 목적 |
| :--- | ---: | :--- |
| 권장 VOC | 10 | 핵심 보험 VOC 분석과 기본 발화 대응 |
| 확장 VOC | 2 | 채널·상담 품질의 비교 분석 |
| 모호한 질문 | 2 | 정보가 부족할 때 추가 확인 요청 |
| 복합 불만 | 2 | 두 문제의 연계 영향과 우선순위 분석 |
| 데이터 없음 | 2 | 무관한 주제에 대한 안전한 0건 처리 |
| 장애 상황 | 2 | Retriever 중단·CSV 누락 대응 |

총 20개, Judge 대상 18개, pytest 장애 대상 2개 구성은 유지했다.

## 질문 개선 방향

### 분석 요청형으로 변경

- TC-01: 모바일 앱 자동차 보험 갱신 오류 분석
- TC-02: 팩스·이메일 청구 서류 접수 확인 문제 비교
- TC-03: 보험금 지급 지연과 결과 설명 부족 분석
- TC-04: 약관·보장·면책 조건의 복잡성과 설명 부족 분석
- TC-05: 사고 접수 이후 담당자·긴급 지원·후속 처리 지연 분석
- TC-06: 온라인 청약·모바일 입력 오류와 반복 입력 분석
- TC-09: 청구 서류 접수와 일부 지급의 단계별 복합 분석
- TC-10: 보험료 납부·연체·갱신 사전 안내 정책 분석
- TC-11: 전화·온라인 상담 채널의 지연 비교
- TC-12: 상담 태도·전문성·안내 일관성 분석
- TC-15: 사고 처리와 고객센터 지연의 연계 영향 분석
- TC-16: 본인 인증과 납입 내역 미반영의 디지털 흐름 분석

### 의도적으로 유지한 발화형

- TC-07: 오타와 띄어쓰기 오류가 있는 보험금 청구 거절 질문
- TC-08: 구체적 정보가 없는 모바일 앱 이상 질문
- TC-13~TC-14: 모호한 앱·서비스 불만

이 케이스들은 분석 요청형과 다른 입력 이해 능력을 확인하기 위해 고객 발화 형태를
유지했다.

### 데이터 없음형 개선

TC-17~TC-18도 단순 문의가 아니라 `현재 VOC 데이터에서 관련 불만을 찾아 분석해 달라`는
형식으로 변경했다. 실제 데이터에 게임 아이템 환불과 반려 로봇 수리 내용이 없으므로
관련 데이터 없음으로 처리하는 것이 정답이다.

## 기대 결과 동기화

질문만 변경하지 않고 다음 필드도 함께 갱신했다.

- 분석 목적에 맞는 `expected_intent`
- 여러 관련 VOC에서 확인할 핵심 `expected_keywords`
- 공통 문제, 고객 영향, 단계별 문제, 채널 비교 등 `required_output`
- 근거 없는 처리 완료·면제·지급 확정과 개인정보 요구 등 `prohibited_output`

## API 없는 검증 결과

- JSON 파싱: 정상
- 총 케이스: 20개
- 유형: 기존 6개 유형과 개수 유지
- Judge 대상: 18개
- pytest 장애 대상: 2개
- 필수 필드 누락: 0건
- 중복 case_id: 0건
- 관련 단위 테스트: `45 passed`
- 분석형 질문의 로컬 보조 검색 결과: 대부분 3~10건의 관련 후보 확인

실제 LLM Judge와 외부 API는 실행하지 않았다.

## 실행 시 주의

기존에 중단된 Judge 보고서는 이전 질문 기준의 결과다. 새로운 테스트 케이스로 최종
보고서를 만들 때는 서버 6개를 다시 시작하고 LLM Judge를 처음부터 실행해야 한다.

`_docs/example_Don't touch` 폴더는 수정하지 않았다.
