# 테스트 케이스 단일 원본 통합 기록

## 목적

기존에는 `test_cases.json`과 `judge_cases.json`에 동일한 질문이 중복되어 수정 시 서로
달라질 위험이 있었다. 모든 테스트와 LLM Judge 보고서가 `test_cases.json` 하나를 기준으로
동작하도록 통합했다.

> `_docs/example_Don't touch` 폴더는 이번 작업에서 열거나 수정하지 않았다.

## 통합 구조

각 테스트 케이스는 질문과 기대 결과, Judge 실행 정책을 함께 가진다.

```json
{
  "case_id": "TC-01",
  "category": "권장 VOC",
  "judge_enabled": true,
  "judge_mode": "live",
  "question": "결제는 완료되었는데 주문 내역에 보이지 않습니다.",
  "expected_intent": "결제 완료 후 주문 조회 실패",
  "expected_keywords": ["결제", "주문 내역"],
  "required_output": ["원인 추정", "고객 안내", "개선안", "우선순위"],
  "prohibited_output": ["근거 없는 환불 확정"]
}
```

`judge_cases.json`은 삭제했고 LLM Judge가 `test_cases.json`을 직접 읽도록 변경했다.
기대 결과도 Judge 입력에 포함하여 질문별 요구사항과 금지사항을 채점 근거로 사용한다.

## 20개 케이스 실행 정책

| 범위 | Judge 정책 | 보고서 표시 |
| :--- | :--- | :--- |
| TC-01~18 | `judge_enabled=true`, 실제 6개 에이전트 실행 | 9개 항목 점수와 총점 |
| TC-19~20 | `judge_enabled=false`, pytest 장애 검증 | `pytest 전용` |

TC-19는 Retriever 중단, TC-20은 CSV 누락을 재현한다. LLM Judge가 실행 중인 서버를
임의로 끄거나 파일 상태를 바꾸지 않도록 두 케이스는 pytest 장애 테스트가 담당한다.
LLM Judge 보고서에는 20개 케이스가 모두 행으로 나타나지만 평균 점수는 실제로 채점된
TC-01~18만 사용한다.

## GUI 버튼 동작

GUI의 `LLM Judge 실행` 버튼은 다음 순서로 동작한다.

1. `test_cases.json`의 20개 케이스 로드
2. TC-01~18의 6개 에이전트 파이프라인 실행
3. 기대 결과와 중간 산출물을 9개 항목으로 채점
4. TC-19~20을 `pytest 전용`으로 기록
5. CSV, 품질 점수, 최종 판정 보고서 저장

API 사용량과 실행시간이 크므로 6개 에이전트가 모두 준비된 상태에서 실행해야 한다.

## 2026-07-13 검증 결과

```text
test_cases.json 전체: 20개
LLM Judge 실제 대상: 18개
pytest 장애 전용: 2개
관련 단위 테스트: 41 passed
전체 테스트: 64 passed, 15 skipped
실패 테스트: 0
```

건너뛴 테스트는 에이전트 서버 6개가 필요한 E2E 항목이다. 이번 검증에서는 실제 LLM API를
호출하지 않았다.
