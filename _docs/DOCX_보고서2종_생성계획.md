# DOCX 보고서 2종 생성 계획

## 1. 목적

LLM Judge와 pytest 실행이 끝난 뒤 생성되는 로그·CSV·Markdown·JSON을 종합하여 다음
두 개의 한글 DOCX 보고서를 생성한다.

```text
D:\voc\quality_diagnosis\reports\VOC_개선_QA_점검완료보고서.docx
D:\voc\quality_diagnosis\reports\VOC_분석_종합품질평가보고서.docx
```

예시 DOCX는 포함해야 할 내용의 종류만 참고한다. 문서의 레이아웃, 표, 그래프, 색상,
문장과 결론은 현재 프로젝트 데이터에 맞춰 새롭게 구성한다.

## 2. 생성 전 완료 조건

최종 보고서는 다음 조건이 충족된 경우에만 생성한다.

- LLM Judge 실행 로그의 `status`가 `completed`
- Judge 대상 18개 케이스의 처리가 모두 종료됨
- `llm_judge_result.csv` 저장 완료
- `quality_score_report.md` 저장 완료
- pytest 실행 로그의 `status`가 `completed`
- 보고서에 사용할 pytest 실행을 사용자가 최종 실행 결과로 지정함

Judge가 `running`, `interrupted`, `failed` 상태이거나 처리 건수가 18개 미만이면 최종
완료보고서를 만들지 않는다. 필요할 경우 파일명과 표지에 `중간보고서`를 명시한 별도
문서만 생성한다.

API 실패로 N/A가 발생했더라도 Judge 실행 자체가 정상 종료되었다면 보고서를 생성할 수
있다. 이때 N/A 건수와 재시도 실패 원인을 본문과 결론에 반드시 표시한다.

## 4. 공통 디자인 방향

두 문서는 긴 설명을 연속해서 배치하는 형식이 아니라 표와 그래프를 중심으로 구성한다.

- A4 세로형 본문, 필요한 대형 표만 가로형 페이지 사용
- 표지, 목차, 전체 결과 요약, 상세 분석, 결론, 부록 순서
- 문서별 대표 색상을 지정하되 동일한 글꼴과 표 스타일 사용
- 점수와 상태는 색상만으로 구분하지 않고 글자와 아이콘을 함께 사용
- 표 머리글 반복, 페이지 번호, 생성 일시, 실행 ID 표시
- 표·그래프 아래에 수치의 의미를 설명하는 짧은 해석 문장 배치
- 원본 파이프라인 출력은 본문을 복잡하게 만들지 않도록 부록에 배치

### 4.1 상태 색상

| 상태 | 색상 |
| :--- | :--- |
| 90점 이상 / 배포 가능 | 녹색 |
| 80~89점 / 조건부 배포 | 파란색 |
| 70~79점 / 주요 개선 필요 | 주황색 |
| 69점 이하 / 배포 보류 | 빨간색 |
| N/A / 미평가 | 회색 |
| 즉시 배포 보류 | 진한 빨간색 |

### 4.2 평가 기준 반영 원칙

동료평가와 교수평가 기준은 보고서의 내부 검수 기준으로만 사용한다. 최종 문서에
`동료평가 1번`, `교수평가 5번`, `평가기준 대응표`와 같은 표현을 직접 넣지 않는다.

본문은 다음과 같은 실제 프로젝트 진행 순서로 자연스럽게 설명한다.

```text
프로젝트를 시작한 이유와 해결하려는 문제
→ 6개 에이전트 구조와 역할 분담
→ VOC가 분석되고 개선안으로 이어지는 과정
→ 내부 테스트와 단계별 품질 점검
→ 독립 LLM Judge가 필요한 이유와 평가 결과
→ 실행 중 발견한 오류·결함과 조치 과정
→ 정량 결과와 생성된 산출물
→ 팀 작업 과정, 남은 한계와 다음 개선 방향
→ 작성자 의견과 최종 결론
```

이 흐름 안에서 프로젝트 목적, 고객 불만 분석, 개선안의 타당성, 에이전트 역할,
내부 품질진단, 독립 평가, 테스트 결과, 장애·결함관리, 발표 전달력, 협업,
요구사항 충족, 정량 성과, 증적관리와 잔여 위험이 자연스럽게 확인되도록 작성한다.

평가 기준 충족 여부는 DOCX 생성 후 내부 검수 과정에서만 대조한다. 평가표의 문장을
본문 제목으로 복사하거나 항목별 예상 점수를 자체적으로 부여하지 않는다.

프로젝트의 구조, 테스트 범위, 실행 결과, 장애 대응, 결함 조치와 잔여 위험을 종합하여
현재 실습 범위에서 QA 점검이 어느 수준까지 완료되었는지 설명한다.

### 5.2 권장 구성

1. 표지
2. 전체 결과 요약
3. 프로젝트와 QA 범위
4. 6개 에이전트 및 전체 처리 흐름
5. 테스트 구성과 역할 분리
6. pytest 정량 결과
7. MCP·E2E·장애 대응 결과
8. LLM Judge 수행 현황 요약
9. API 재시도 및 N/A 처리 현황
10. 결함·조치·재검증 현황
11. 잔여 위험과 개선 권고
12. 작성자 종합 의견
13. QA 완료 결론
14. 산출물 및 실행 증적

### 5.3 주요 표

- 전체 테스트·통과·실패·SKIP 요약표
- 테스트 파일별 수행 건수와 상태표
- 6개 에이전트 역할 및 API 사용표
- pytest와 LLM Judge의 역할 비교표

### 5.5 최종 판단 방식

pytest의 실패가 없더라도 SKIP과 미재현 장애 조건을 별도로 설명한다. LLM Judge의 평균
점수와 N/A도 함께 확인하되, QA 완료와 VOC 결과 품질을 같은 의미로 단정하지 않는다.

결론은 다음 세 가지 중 실제 결과에 맞는 표현을 선택한다.

- 실습 범위 QA 점검 완료
- 조건부 완료, 개선 후 재검증 필요
- 점검 미완료, 실패·중단 항목 조치 필요

빈 원형 그래프 대신 `N/A 0건` 요약 카드와 설명을 사용한다.

## 7. 작성자 의견과 결론 작성 원칙

문서 마지막의 의견과 결론은 정형 문구를 붙이는 방식이 아니라, 표·그래프·상세 근거를
검토한 작성자가 직접 판단한 것처럼 자연스럽게 작성한다.

- 실제 수치와 사례 ID를 근거로 사용
- 잘된 점과 부족한 점을 균형 있게 설명
- 낮은 평가 항목이 어떤 케이스에서 반복됐는지 연결
- 실패·SKIP·N/A·중단을 숨기지 않고 의미를 설명
- 수업 실습, 팀 비교, 발표용 프로젝트라는 범위를 반영
- 다음 개선의 우선순위와 재검증 방법을 구체적으로 제시
- `완벽하다`, `업계 최상위`, `즉시 운영 가능`과 같은 과장 표현 배제
- 실제 근거가 없는 수치, 정책, 성과를 새로 만들지 않음

### 7.1 QA 점검완료보고서 의견 초점

- 테스트 범위가 프로젝트 구조를 충분히 검증했는가
- 서버·MCP·장애 대응과 로그 추적성이 확인됐는가
- SKIP이나 미재현 조건이 최종 판단에 어떤 영향을 주는가
- 현재 실습 범위에서 완료로 판단할 수 있는가

### 7.2 종합품질평가보고서 의견 초점

- 18개 결과에서 반복된 강점과 약점은 무엇인가
- 어떤 에이전트와 평가 항목을 먼저 개선해야 하는가
- 최종 점수와 배포 판정의 근거가 타당한가
- 개선 후 어떤 케이스로 재검증해야 하는가

## 8. 생성 방식

DOCX 생성 기능은 LLM Judge 코드와 분리된 별도 보고서 생성 모듈로 구성한다.

```text
pytest 및 LLM Judge 실행
        ↓
JSON·LOG·CSV·MD 저장
        ↓
보고서 데이터 검증 및 통합
        ↓
표·그래프 생성
        ↓
DOCX 2종 생성
        ↓
페이지·표·그래프·한글 표시 최종 확인
```

수치 집계와 표 생성은 구조화된 JSON·CSV를 기준으로 결정적으로 수행한다. Markdown은 상세
근거와 실제 파이프라인 결과를 가져오는 용도로 사용한다. 작성자 의견은 집계된 수치와
반복 패턴을 근거로 작성하되 최종 문장과 판단은 전체 결과와 모순되지 않는지 검증한다.

## 9. 생성 후 검수 항목

- 한글 파일명과 문서 제목이 일치하는가
- Judge 처리 건수가 18개인지 표시됐는가
- pytest 통과·실패·SKIP 수치가 로그와 일치하는가
- 9개 항목 점수 합계와 총점이 CSV와 일치하는가
- N/A와 즉시 보류 조건이 누락되지 않았는가
- 중간 결과를 최종 완료로 표현하지 않았는가
- 표가 페이지 밖으로 잘리거나 행이 겹치지 않는가
- 그래프의 제목·범례·축·단위가 한글로 표시되는가
- 원본 로그와 API 키·민감정보가 문서에 노출되지 않는가
- 결론의 모든 판단이 본문 수치와 근거로 추적 가능한가

## 10. 보호 원칙

`_docs/example_Don't touch` 폴더의 예시 문서는 읽기 참고만 하며 수정하거나 덮어쓰지
않는다. 생성되는 DOCX는 모두 `quality_diagnosis/reports`에 새 파일로 저장한다.
