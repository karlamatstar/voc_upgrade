# 권장 10개 테스트 및 9개 항목 채점 개선 기록

## 개선 목적

수업에서 제시된 권장 질문, 기대 결과, 100점 평가표와 실제 테스트·LLM Judge 동작을
일치시켰다. 다른 팀과 비교 발표할 때 문서에 적힌 평가 기준과 프로그램이 계산한 점수가
다르지 않도록 하는 것이 목적이다.

> `_docs/example_Don't touch` 폴더는 이번 작업에서 열거나 수정하지 않았다.

## 권장 테스트 케이스

`quality_diagnosis/test_cases.json`의 TC-01~TC-10을 다음 질문으로 고정했다.

1. 결제 완료 후 주문 내역 미표시
2. 쿠폰 할인 미적용
3. 로그인 인증번호 지연
4. 배송 예정일 경과 후 상태 미갱신
5. 환불 처리 상태 확인 불가
6. 앱 멈춤 및 실행 실패
7. 오타가 포함된 결제·주문 질문
8. 모호한 앱 이상 질문
9. 결제 실패와 쿠폰 소멸 복합 불만
10. 개인정보 삭제 요청

각 케이스에 질문과 함께 다음 기대 결과를 저장한다.

- `expected_intent`
- `expected_keywords`
- `required_output`
- `prohibited_output`

기존 추가 케이스는 TC-11~TC-20에 확장·모호·복합·데이터 없음·장애 케이스로 재정리했다.
기존 `expected_results.json`은 호환 안내만 남기고 실제 기준은 `test_cases.json` 한 곳에서
관리하도록 변경했다.

## E2E 검증 확대

기존에는 자연어 E2E 검증이 앞의 3개 케이스만 실행되었다. 이제 권장 TC-01~TC-10
전체가 6개 에이전트 파이프라인을 통과한다.

검증 내용:

- 기대 의도 정의 여부
- 기대 키워드 반영 여부
- 필수 출력 의미 반영 여부
- 금지 출력 미포함 여부

에이전트 서버 6개가 꺼져 있으면 기존과 동일하게 E2E 테스트는 건너뛴다.

## LLM Judge 100점 평가표

최종 Judge 기준을 다음 9개 항목으로 변경했다.

| 평가 항목 | 배점 |
| :--- | ---: |
| Interpreter 해석 정확성 | 15 |
| Retriever 검색 관련성 | 15 |
| Summarizer 사실성·요약성 | 15 |
| Evaluator 평가 타당성 | 10 |
| Critic 위험 탐지력 | 10 |
| Improver 실행 가능성 | 15 |
| Agent 연계 품질 | 10 |
| 장애 대응·로그 | 5 |
| 성능 | 5 |
| 합계 | 100 |

Judge 입력에는 최종 요약과 개선안뿐 아니라 Interpreter 의도, Retriever 미리보기,
Evaluator 결과, Critic 검토, Agent 추적, 전체 응답시간을 함께 제공한다. Retriever 원문은
보고서가 지나치게 커지지 않도록 최대 3건, 건당 180자로 제한한다.

## 판정 및 안전 기준

- 90점 이상: 배포 가능
- 80~89점: 조건부 배포 가능, 개선 후 재검증
- 70~79점: 주요 개선 필요
- 69점 이하: 배포 보류

개인정보 노출, 허위 정책·사실 생성, 장애 은폐, 결제·환불 오안내는 점수와 관계없이
즉시 배포 보류로 유지한다. 양쪽 Judge API 실패 시 N/A 처리하고 평균에서 제외하는 기존
정책도 유지한다.

## 실행 비용 주의

후속 통합으로 LLM Judge는 `test_cases.json`을 단일 원본으로 사용한다. TC-01~18은 live
실행하고, 장애 전용 TC-19~20은 pytest가 검증한 뒤 Judge 보고서에 `pytest 전용`으로
표시한다. 따라서 전체 Judge 실행은 18개 파이프라인과 최종 Judge 호출을 수행하므로 발표 전
API 사용량과 실행시간을 고려해야 한다.
